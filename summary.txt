1. DATABASE DESIGN
================================================================================

PRINCIPLES
- Money = BIGINT in minor units. Never NUMERIC, never FLOAT.
- UUID v4 primary keys (native uuid type, 16 bytes).
- timestamptz everywhere. Never plain timestamp.
- created_at + updated_at on every table. No soft deletes (YAGNI).
- Enums as TEXT + CHECK constraint (not PG ENUM type).
- Foreign keys with explicit ON DELETE behavior.
- Indexes justified by a specific query. No speculative indexes.


ERD

  users
    id             uuid   PK
    email          citext UNIQUE
    password_hash  text
    name           text
    created_at     timestamptz
    updated_at     timestamptz

  orders                              (users 1 --- N orders)
    id             uuid   PK
    user_id        uuid   FK -> users (ON DELETE CASCADE)
    product_name   text
    amount         bigint             minor units
    currency       char(3)            ISO-4217
    status         text               pending|paid|failed|cancelled
    receipt_url    text NULL
    created_at     timestamptz
    updated_at     timestamptz

  payments                            (orders 1 --- 1 payments)
    id             uuid   PK
    order_id       uuid   FK -> orders  UNIQUE  (ON DELETE CASCADE)
    amount         bigint             snapshot from order
    currency       char(3)
    status         text               pending|processing|paid|failed
    provider_ref   text NULL
    attempt_count  int
    last_error     text NULL
    created_at     timestamptz
    updated_at     timestamptz
    finalized_at   timestamptz NULL

  webhook_events                      (idempotency + audit ledger)
    event_id       text   PK          provider's unique event id
    payment_id     uuid   FK -> payments NULL
    signature      text
    payload        jsonb
    received_at    timestamptz
    processed_at   timestamptz NULL
    status         text               received|processed|failed


INDEXES (only 3, every one justified)
- users:           UNIQUE(email)                       -- login + registration
- orders:          INDEX(user_id, created_at DESC)     -- list orders paginated
- payments:        UNIQUE(order_id)                    -- enforces 1:1
- webhook_events:  PRIMARY KEY(event_id)               -- idempotency
                   INDEX(payment_id)                   -- audit history query


TABLES EXPLICITLY REJECTED
- sessions / refresh_tokens (spec: JWT 24h only)
- products / product_catalog (product is a string, no SKU logic)
- audit_log (webhook_events covers it)
- order_items (no line items in spec)
- roles / permissions (single role: authenticated user)
- outbox table (would contradict in-memory queue requirement)


MIGRATIONS LAYOUT (one migration per table, real down migrations)

2. API CONTRACT
================================================================================

RESPONSE ENVELOPE
  Success: { "success": true,  "data": {...} }
  Error:   { "success": false, "error": { "code": "...", "message": "..." } }

PAGINATION (offset-based)
  Query: ?page=1&page_size=20   (default 20, max 100)
  Response data:
    {
      "items": [...],
      "pagination": {
        "page": 1, "page_size": 20,
        "total_items": 143, "total_pages": 8
      }
    }


ENDPOINTS

AUTH
  POST /api/v1/auth/signup
    body: { email, password (8-72), name }
    201:  { user, token }
    codes: 400 INVALID_REQUEST | 409 EMAIL_ALREADY_EXISTS | 429 RATE_LIMITED
    rate limit: 5/min per IP

  POST /api/v1/auth/login
    body: { email, password }
    200:  { user, token }
    codes: 400 | 401 INVALID_CREDENTIALS (no enumeration) | 429
    rate limit: 5/min per IP


ORDERS  (all require Bearer JWT; enforce user_id == JWT.sub)
  POST   /api/v1/orders
    body: { product_name, amount>0, currency (3-char whitelisted) }
    201:  { order }   (side effect: enqueue payment job)

  GET    /api/v1/orders?page=&page_size=          (CACHED in Redis)
  GET    /api/v1/orders/:id
  PATCH  /api/v1/orders/:id                       (only when status=pending)
    body: { product_name?, receipt_url? }         (amount/currency IMMUTABLE)
  DELETE /api/v1/orders/:id                       (only when status=pending)
  GET    /api/v1/orders/:id/payment               (payment status view)

  404 (not 403) for other users' resources -> prevents ID enumeration
  409 ORDER_NOT_MUTABLE if trying to modify a non-pending order


WEBHOOK  (external, no JWT)
  POST /webhooks/payment
    headers: X-Signature, X-Timestamp, X-Event-Id
    body:    { event_id, payment_id, status, provider_ref, occurred_at }
    200: verified + processed (or duplicate)
    400 MISSING_HEADERS | 400 EXPIRED_TIMESTAMP | 401 INVALID_SIGNATURE
    5xx only on internal failure (signals provider retry)


UPLOAD
  POST /api/v1/uploads   (multipart/form-data)
    field: file
    validation: MIME whitelist (jpeg, png, pdf), size <= 5MB
    201: { url, filename, size, mime }
    (Does NOT auto-attach to order; client PATCHes receipt_url.)


HEALTH
  GET /healthz  -- liveness (200 if process up)
  GET /readyz   -- readiness (checks DB + Redis, 503 if either down)


STATUS CODE DISCIPLINE
  200 OK | 201 Created | 204 No Content
  400 client error | 401 unauthenticated | 404 not found (or hidden)
  409 business conflict | 429 rate limited
  500 internal | 503 not ready / webhook internal retry signal
  (422 NOT USED. 400 covers validation.)

3. DOMAIN MODEL
================================================================================

PHILOSOPHY: rich where invariants exist, plain data elsewhere. No smart models
that reach into repositories. Strict DTO <-> domain separation.

User
  fields: ID, Email, PasswordHash, Name, CreatedAt, UpdatedAt
  behavior: CheckPassword(plain) bool  (bcrypt encapsulated)

Order
  fields: ID, UserID, ProductName, Amount, Currency, Status, ReceiptURL,
          CreatedAt, UpdatedAt
  behavior:
    CanBeModified() bool          (status == pending)
    CanBeDeleted()  bool          (status == pending)
    MarkPaid/MarkFailed/MarkCancelled -> validate transitions in memory
  invariant: Amount > 0, Currency valid ISO code
  relationship: 1:1 with Payment (loaded via repository)

Payment
  fields: ID, OrderID, Amount, Currency, Status, ProviderRef, AttemptCount,
          LastError, CreatedAt, UpdatedAt, FinalizedAt
  behavior:
    Transition(newStatus) error   -- central state machine:
        pending    -> processing | failed
        processing -> paid | failed
        paid       -> (terminal)
        failed     -> (terminal)
    IsTerminal() bool
    IncrementAttempt()

WebhookEvent
  pure ledger record. No behavior. Anemic on purpose.

Money value object -- REJECTED. Currency comparison happens in only two places.
Add when we have FX/multi-currency baskets.


================================================================================
4. CACHE STRATEGY (Redis)
================================================================================

SCOPE: cache only GET /orders (list). Nothing else.

KEY PATTERNS (entire Redis surface)
  orders:user:{user_id}:page:{page}:size:{page_size}   TTL 5min   list cache
  ratelimit:{ip}:{endpoint}                            TTL 60s    rate limit
  webhook:event:{event_id}                             TTL 24h    replay guard

TTL: 5 minutes on list cache. Safety net if invalidation fails.
     Primary correctness mechanism = explicit invalidation.

INVALIDATION TRIGGERS
  - order create/update/delete
  - payment status change (worker or webhook)
  Payment path: worker/webhook must load user_id via payment -> order chain.

APPROACH: SCAN orders:user:{uid}:* + pipelined DEL.
  Rejected the "per-user index SET" approach - more code, another failure mode.

CACHE MISS FLOW
  GET Redis -> hit: return
              miss: query DB -> SET (5min TTL) -> return

NOT CACHED
  - GET /orders/:id (single-row lookup, ~1ms from PG)
  - GET /users/me (identity in JWT claims)
  - payment status (async changes, brittle invalidation)

FAILURE POLICY
  Cache read error -> treat as miss (never fail-close on cache).
  Cache write error -> log and continue.
  DB commit succeeds + cache invalidation fails -> log error, DO NOT rollback.


================================================================================
5. BACKGROUND JOB DESIGN
================================================================================

STRUCTURE
  - Buffered chan Job (capacity 1000, configurable)
  - Fixed pool of 4 goroutines
  - Retry: worker sleeps in-place (does NOT re-enqueue)
  - Graceful shutdown: context.Context + sync.WaitGroup + errgroup

JOB ENVELOPE
  Job {
    ID          string        // uuid, correlation
    Type        string        // "payment.process"
    Payload     []byte        // job-type-specific JSON
    Attempt     int           // starts at 1
    MaxAttempts int           // default 3
    EnqueuedAt  time.Time
  }

RETRY / BACKOFF
  Attempt 1 -> sleep 1s
  Attempt 2 -> sleep 2s
  Attempt 3 -> sleep 4s
  Formula: 2^(attempt-1) seconds  +/-20% JITTER (prevents thundering herd)

  Retry on:    5xx from provider, network errors, timeouts
  Don't retry: 4xx (permanent), marshal errors, context.Canceled

WORKER LIFECYCLE
  main:
    queue := NewQueue(bufferSize)
    pool  := NewPool(N, queue, paymentService)
    pool.Start(ctx)          -- spawns goroutines
    HTTP server runs
    on SIGINT/SIGTERM:
      server.Shutdown()
      cancel(ctx)
      pool.Wait() with 30s deadline
      close DB / Redis


HAPPY PATH SEQUENCE

  Client   HTTP    OrderSvc   Queue   Worker   Provider   WebhookH   PaymentSvc
    |       |         |         |       |         |          |           |
    |POST-->|         |         |       |         |          |           |
    |       |-Create->|         |       |         |          |           |
    |       |         |-BEGIN TX|       |         |          |           |
    |       |         | INS ord |       |         |          |           |
    |       |         | INS pmt |       |         |          |           |
    |       |         |-COMMIT  |       |         |          |           |
    |       |         |-Invalidate cache|         |          |           |
    |       |         |-Enqueue>|       |         |          |           |
    |       |<-201----|         |       |         |          |           |
    |<-201--|         |         |       |         |          |           |
    |       |         |         |-Job-->|         |          |           |
    |       |         |         |       |-POST--->|          |           |
    |       |         |         |       |<-202----|          |           |
    |       |         |         |       |         |-cb------>|           |
    |       |         |         |       |         |          |-Verify-->|
    |       |         |         |       |         |          |    HMAC OK
    |       |         |         |       |         |          |    ts OK
    |       |         |         |       |         |          |    INS webhook_events (UNIQUE)
    |       |         |         |       |         |          |    UPDATE payment (guarded)
    |       |         |         |       |         |          |    UPDATE order.status
    |       |         |         |       |         |          |    Invalidate cache
    |       |         |         |       |         |          |<-200-----|


RETRY PATH

  Worker                         Provider
    |------- POST --------------->|
    |<------ 503 -----------------|   transient
    |
    |--- backoff 1s (+/- jitter) -|
    |------- POST --------------->|
    |<------ 503 -----------------|
    |
    |--- backoff 2s (+/- jitter) -|
    |------- POST --------------->|
    |<------ 503 -----------------|
    |
    | max attempts reached
    |--- UPDATE payment status=failed, last_error=...
    |--- UPDATE order   status=failed
    |--- Invalidate cache
    |--- slog.Error

  Note: retry sleep uses select { <-ctx.Done() | <-time.After(backoff) }
        so shutdown interrupts sleep immediately.


================================================================================
6. WEBHOOK DESIGN
================================================================================

THREAT MODEL
  - Replay of legitimate webhooks
  - Forgery of "paid" events
  - Garbage bodies
  - Delayed-timestamp sneak-ins

SIGNATURE SCHEME
  algorithm: HMAC-SHA256
  signed:    timestamp + "." + raw_body_bytes
  encoding:  hex (documented)
  secret:    WEBHOOK_SECRET (>= 32 bytes, from env)

HEADERS
  X-Signature:  hex(hmac_sha256(secret, timestamp + "." + body))
  X-Timestamp:  <unix seconds>
  X-Event-Id:   <provider's unique event id>


VERIFICATION FLOW (fail-fast, corrected order)
  1. Required headers present?           -> 400 MISSING_HEADERS
  2. Timestamp is valid integer?         -> 400 INVALID_TIMESTAMP
  3. |now - timestamp| <= 300s?          -> 400 EXPIRED_TIMESTAMP
  4. Recompute HMAC + constant-time cmp  -> 401 INVALID_SIGNATURE  (hmac.Equal)
  5. Redis GET webhook:event:{event_id}
        found -> 200 duplicate
        else  -> proceed
  6. Parse body / validate schema        -> 400 INVALID_REQUEST
  7. BEGIN TX
       INSERT webhook_events (event_id UNIQUE)
         conflict -> ROLLBACK, return 200 (duplicate racing us)
         ok       -> proceed
       SELECT payment FOR UPDATE
       Validate transition
       UPDATE payment
       UPDATE order.status
     COMMIT
  8. Redis SET webhook:event:{event_id} EX 86400
  9. Invalidate orders list cache
 10. Return 200


IDEMPOTENCY GUARANTEES (belt-and-suspenders)
  - Postgres UNIQUE(event_id) on webhook_events = SOURCE OF TRUTH
  - Redis fast-path = latency optimization only
  Redis SET only AFTER DB commit, otherwise stale keys block real retries.


FAILURE POLICY
  DB down    -> return 5xx (provider retries)
  Redis down -> proceed with DB-only check (still safe, just slower)


REQUEST EXAMPLE

  POST /webhooks/payment HTTP/1.1
  Host: api.example.com
  Content-Type: application/json
  X-Signature: 5f2a...c891
  X-Timestamp: 1721721600
  X-Event-Id:  e_01H8Z...

  {
    "event_id":     "e_01H8Z...",
    "payment_id":   "b3d6...",
    "status":       "paid",
    "provider_ref": "prov_98765",
    "occurred_at":  "2026-07-23T09:00:00Z"
  }


SIGNATURE GENERATION (pseudocode)
  data = "1721721600" + "." + raw_body_bytes
  sig  = hex(HMAC_SHA256(secret, data))

7. AUTH DESIGN
================================================================================

JWT
  algorithm: HS256 (shared secret; RS256 unjustified for monolith)
  claims: {
    sub:   <user_uuid>,        // required
    email: "...",              // saves DB read on /users/me
    name:  "...",              // saves DB read
    iat:   ...,
    exp:   iat + 24h,          // hard requirement
    iss:   "order-mock-payment",
    jti:   <uuid>              // enables future revocation via denylist
  }
  Trade-off: name/email stale until re-login. Acceptable.

MIDDLEWARE
  - Extract Authorization: Bearer <token>
  - Missing -> 401 UNAUTHORIZED
  - Assert token.Method == HS256 (defense vs alg-confusion attack)
  - Verify signature + exp + iat + iss
  - c.Set("user_id", uid) from sub
  - NEVER read user_id from body/query

AUTHORIZATION PATTERN
  requesterID := c.MustGet("user_id")
  resource, err := repo.GetByID(ctx, resourceID)
  if resource.UserID != requesterID { return 404 }   // 404, not 403

TOKEN LIFECYCLE
  - Issued on signup + login
  - Expires after 24h
  - NO refresh token (out of scope)
  - NO revocation (documented; add via Redis jti denylist if needed later)

PASSWORD SECURITY
  - bcrypt cost 12
  - password validated <= 72 bytes (bcrypt truncation guard)
  - dummy bcrypt on "user not found" (defeats timing enumeration)
  - never log passwords or hashes

SIGNUP ENUMERATION
  409 EMAIL_ALREADY_EXISTS is accepted (matches user expectation).
  Mitigation: rate limit 5/min per IP.

8. FILE UPLOAD DESIGN
================================================================================

STORAGE LAYOUT (date-partitioned, avoids single-dir blowout)
  /app/data/uploads/YYYY/MM/DD/<ulid_or_uuid>.<ext>

FILENAME GENERATION
  - Never trust user-supplied filename.
  - Filename: {ulid_or_uuid}.{safe_ext}
  - Extension derived from DETECTED MIME, not from client's filename.

VALIDATION
  1. Size: Content-Length quick reject + http.MaxBytesReader (never trust header)
       max 5MB
  2. MIME: net/http.DetectContentType on first 512 bytes of actual file bytes
       whitelist: image/jpeg, image/png, application/pdf
  3. Extension derived from detected MIME.

PATH TRAVERSAL DEFENSE
  - Base dir is fixed absolute path (config)
  - finalPath = filepath.Join(baseDir, datePath, generatedFilename)
  - Assert strings.HasPrefix(filepath.Clean(finalPath), baseDir)
  - Never use any client string in the path.

PUBLIC URL
  {BASE_URL}/uploads/YYYY/MM/DD/{filename}
  Served by Gin static handler.
  No auth on read (URLs are UUIDs -> unguessable). Trade-off for demo scope.

REJECTED
  - S3 (spec: local disk)
  - Thumbnails / image processing
  - Virus scanning (would want clamav in real prod)
  - Auto-attach to order (upload returns URL, client PATCHes receipt_url)

11. RISK REVIEW
================================================================================

ARCHITECTURAL
  - In-memory queue loses jobs on crash
      -> Documented loudly in README "Known Limitations"
  - Cache invalidation could silently fail
      -> slog.Error on failure + 5min TTL backstop
  - Vertical slice duplication
      -> Accept until rule of three
  - orders.status vs payments.status drift
      -> Single-writer discipline: payment.Service owns both, same TX

SECURITY
  - SQL injection            -> sqlx parameterized; golangci-lint sqlclosecheck
  - JWT forgery              -> HS256 w/ >=32-byte secret from env
  - JWT alg-confusion        -> Explicit assert method == HS256
  - Password brute force     -> bcrypt cost 12 + login rate limit 5/min/IP
  - Login enumeration        -> Same 401 msg + dummy bcrypt on unknown email
  - Webhook forgery          -> HMAC + constant-time + timestamp + idempotency
  - Webhook replay           -> event_id UNIQUE (DB) + Redis fast-path + <=5min
  - Path traversal           -> Fixed base dir + generated filename + HasPrefix
  - ID enumeration           -> UUID PKs + 404 (not 403) for foreign resources
  - Hash leakage in logs     -> Never marshal User; DTOs don't have hash field
  - X-Forwarded-For spoofing -> Trust only from configured proxy IPs
  - Signup enumeration       -> Accepted trade-off; rate-limited
  - Bcrypt >72 byte silent truncation -> Reject at validation

SQL
  - N+1 in list orders            -> single SELECT with LEFT JOIN if needed
  - Missing WHERE on ownership    -> repo method signature requires userID
  - Race on order/payment state   -> SELECT FOR UPDATE + guarded UPDATE
  - Missing indexes -> seq scans  -> only 3 indexes, verified with EXPLAIN
  - Migrations not idempotent     -> golang-migrate + real down files
  - Timezone bugs                 -> timestamptz + UTC in Go layer

CONCURRENCY
  - Two workers same job          -> impossible: channel semantics
  - Worker goroutine leak         -> ctx-driven select + WaitGroup 30s deadline
  - Retry sleep uninterruptible   -> select { <-ctx.Done() | <-time.After }
  - DB pool exhaustion            -> MaxOpenConns set explicitly (25)
  - Redis pool exhaustion         -> go-redis default + monitored
  - Data race on shared state     -> stateless state machine; no shared mutables

CACHE
  - Stale list after write    -> invalidate immediately + log failure + TTL
  - Cross-user data leak      -> key includes user_id; unit-tested
  - Redis down -> app down    -> cache read errors treated as miss (fail-open)
  - SCAN slow at scale        -> per-user pagination -> single-digit keys
  - Rate-limit TTL bug        -> SETNX + EXPIRE atomic

WEBHOOK
  - Verification bypass          -> strict fail-fast ordering
  - Race on duplicate webhooks   -> UNIQUE(event_id) + SELECT FOR UPDATE
  - Clock skew                   -> +/-5min window + NTP required (documented)
  - Wrong status -> forever retry -> 200 on success AND duplicate
  - DB down at webhook           -> return 5xx so provider retries

TESTING
  - Flaky integration tests   -> Docker Compose up/down; per-test DB truncate
  - Repo tests coupled to sqlx -> service->repo interface, real DB for repo tests
  - Retry tests take real time -> Sleeper interface, mockable
  - Webhook tests unsigned     -> test helper signs with test secret
  - Coverage without meaning   -> 70% target, business-rule tests over lines
